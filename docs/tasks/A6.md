## Goal

One command, `docker compose up`, starts PostgreSQL, runs the pipeline once on a small sample data set, publishes to PostgreSQL and serves the app. It works on a clean machine with only Docker installed. This is the "working build" hand-in and the fallback for the demo.

## Context

- Read `docs/acceptance-criteria.md` section "Hand-ins from the brief", `docs/architecture.md` sections "Data flow" and "Modules", `docs/contracts.md` sections "Paths" and "Serving database", and `docs/setup.md` (F3) for how Spark is run locally.
- Three services: `db` (PostgreSQL), `pipeline` (a one-shot Spark job that exits), `app` (the http4s server). The app talks only to `db`; the pipeline writes Delta tables to a volume and publishes to `db`.
- Sample data must be small (aim for under 5 MB in the repository), public, and enough to show at least one signal, one labeled reaction with a passage, one open recall and one change event. Never commit a full download.
- The app also needs the web pages (A3) and API (A2). A6 depends only on A1 in the backlog; if A2 or A3 is not merged when you start, build and test the `db` and `pipeline` services first and add `app` when A2 lands.

Verify before writing Dockerfiles:

1. How each module is packaged. Building images needs a runnable artifact: a fat jar for `pipeline` (Spark is `provided`, Delta and the JDBC drivers must be inside) and a runnable distribution or fat jar for `app`. F1 adds the `sbt-assembly` plugin and puts the H2 and PostgreSQL drivers in `pipeline` (contracts.md, "Toolchain additions (F1)"); confirm in `project/plugins.sbt` and `build.sbt`. If the plugin is missing, open a `[Chore]` pull request on the build first (F1 owns `build.sbt` and `project/`); do not add plugins from this branch.
2. The orchestrator's main class and arguments (C1), for example `medsignal.run.Main full`. Read `pipeline/src/main/scala/medsignal/run/`.
3. The official Spark image tag matching the Spark 4.0.x and Scala 2.13 in `build.sbt`, with Java 21 (Docker Hub `apache/spark`). Tag names change; pick one that exists and pin it exactly.
4. How config is overridden. The pipeline reads typesafe config through `Settings` (`application.conf` plus every `conf.d/*.conf`), so a system property such as `-Dmedsignal.dataDir=/data` overrides a file value; see `docs/setup.md` and `docs/tasks/A2.md` section "Inputs" for the app's environment variables.
5. Label sections reach the pipeline as JSON Lines in `data/interchange/labels/` written by the `labels` module. For the sample, commit pre-generated JSON Lines and `label_section.ddl` so the compose run does not need the `labels` tool.

## Inputs

- Build artifacts of `pipeline` and `app`.
- Sample files under `docker/sample/`, laid out exactly like `data/raw/<source>/`, `data/reference/` and `data/interchange/labels/`.

## Outputs

- `docker-compose.yml` at the repository root.
- Images `medsignal-pipeline` and `medsignal-app`, built by Compose.
- App on `http://localhost:8080` showing the sample data.

## Files to create

- `docker-compose.yml`: the three services, one named volume for `/data`, one for PostgreSQL.
- `docker/app/Dockerfile`: multi-stage; build with sbt, run on a JRE 21 image.
- `docker/pipeline/Dockerfile`: multi-stage; build the fat jar, run on the Spark image.
- `docker/pipeline/run-sample.sh`: copies the sample into `/data`, runs the full cadence with `spark-submit`.
- `docker/sample/`: sample raw files, reference files and label JSON Lines; `docker/sample/README.md` says where each file came from and how it was cut down.
- `docker/smoke.sh`: waits for the app and checks the endpoints.
- `docker/.env.example`: database name, user and password for local use only.
- `.dockerignore` is at the repository root and is not in the owned paths; keep build context small by setting `context` and copying only what is needed, or ask for the file in a separate `[Chore]` pull request.

## Implementation steps

1. Compose file, shape:

   ```yaml
   services:
     db:
       image: postgres:<pinned major version>
       environment: { POSTGRES_DB: medsignal, POSTGRES_USER: medsignal, POSTGRES_PASSWORD: ${MEDSIGNAL_DB_PASSWORD:-medsignal} }
       healthcheck: { test: ["CMD-SHELL", "pg_isready -U medsignal -d medsignal"], interval: 5s, retries: 12 }
       volumes: [ "pgdata:/var/lib/postgresql/data" ]
     pipeline:
       build: { context: ., dockerfile: docker/pipeline/Dockerfile }
       depends_on: { db: { condition: service_healthy } }
       environment: { MEDSIGNAL_SERVING_URL: "jdbc:postgresql://db:5432/medsignal", ... }
       volumes: [ "lake:/data" ]
     app:
       build: { context: ., dockerfile: docker/app/Dockerfile }
       depends_on: { pipeline: { condition: service_completed_successfully } }
       environment: { MEDSIGNAL_SERVING_URL: "jdbc:postgresql://db:5432/medsignal", ... }
       ports: [ "8080:8080" ]
   volumes: { pgdata: {}, lake: {} }
   ```

   `service_healthy` and `service_completed_successfully` are Compose features; confirm them in the Compose documentation for the version you run. The app starts only after the first publish, so it never shows an empty database.

2. `docker/pipeline/Dockerfile`: stage 1 from an sbt image with JDK 21, copy `build.sbt`, `project/`, `pipeline/`, run the assembly task. Stage 2 from the pinned Spark image, copy the jar, the sample and `run-sample.sh`. The pipeline reads its serving connection from config keys `medsignal.serving.*`; pass them as `--driver-java-options "-Dmedsignal.serving.url=... -Dmedsignal.dataDir=/data"` or whatever mechanism item 4 found.

3. `run-sample.sh`: `set -euo pipefail`; copy `docker/sample/*` into `/data` only if `/data/raw` is empty; run `spark-submit --master "local[*]" --class <C1 main class> <jar> full`; exit with spark-submit's status. A failed quality check must make the container exit non-zero so `app` does not start on bad data.

4. `docker/app/Dockerfile`: stage 1 builds the app artifact; stage 2 from a JRE 21 image, non-root user, `EXPOSE 8080`, entrypoint runs `medsignal.api.Main`.

5. Sample data. Choose two or three formulary drugs with a known story (for example an SGLT2 inhibitor and ketoacidosis). Cut real public files down to the rows for those drugs plus enough background rows for the 2x2 counts to be meaningful; keep the original header lines and delimiters so the real parsers run. Include one deliberately malformed FAERS line so a reject shows on the health page. Record in `docker/sample/README.md` the source URL, the quarter and the filter used for each file.

6. Secrets: the default password is for local demo only. Read it from `MEDSIGNAL_DB_PASSWORD`; commit `.env.example`, never `.env`.

7. `docker/smoke.sh`: poll `http://localhost:8080/api/health` for up to 5 minutes; then require HTTP 200 from `/`, `/api/signals`, `/api/changes`, `/api/recalls?status=open`, and at least one signal in `/api/signals`.

8. Measure and note the cold start time (first `docker compose up --build`) and the warm start time.

## Tests

This task has no Scala code. Verification is the smoke script plus a checklist:

- [ ] `docker compose config` reports no error.
- [ ] On a machine with no JDK, sbt or Spark installed: `git clone`, `docker compose up --build`, then `docker/smoke.sh` exits 0.
- [ ] `docker compose down -v` followed by `docker compose up` gives the same result (nothing depends on leftover state).
- [ ] Second `docker compose up` without `-v`: the pipeline finds its data, re-publishes, the app starts; triage decisions made before are still present.
- [ ] Breaking the sample (delete a required file) makes `pipeline` exit non-zero and `app` not start.
- [ ] The Signals page shows a signal; the drill-down shows a highlighted passage; Recalls shows the sample recall; Pipeline health shows the reject.
- [ ] Image sizes and start times recorded.

## Done when

- [ ] `docker/smoke.sh` passes.
