## Goal

Two stages for the frequent runs. The daily label stage loads only label versions not seen before, so extraction (L5) runs for those versions alone. The weekly recall stage fetches recalls reported since the last run and re-checks every recall we hold as open, so a status change is captured. These make the daily and weekly runs cheap (criterion 3: under 2 minutes).

## Implementation steps

Labels: `LabelIncrementalStage` (`name = "incremental.labels"`, `cadences = Set(Daily)`, conf `after = []`).

1. Read the interchange files with I6's reader function (the one that applies the generated DDL) into `Dataset[LabelSection]`. Do not write a second reader.
2. `NewLabelVersions.select(incoming: Set[(String, Int)], inBronze: Set[(String, Int)]): Set[(String, Int)]` (pure) = incoming minus those already in `bronze.label_section`. The distinct pairs are small enough to collect; if not, do the same with a left-anti join.
3. If nothing is new: return `StageResult(0, 0, 0)`.
4. `Delta.append` the sections of the new pairs to `Tables.bronze("label_section")`. A row I6's reader marks unusable becomes a `Reject`, written with `Rejects.write`, exactly as I6 does it.
5. Call S4's build function to refresh `silver.label_version`. A new version of a reference label moves `isReference` to it, so S4 must re-decide the reference label for the affected `rxcui`s; if S4's function recomputes the whole table that is fine, the table is small.
6. `RunManifest.record("incremental.labels", s"$setId:$version", checksum = "", watermark = Some(newest effectiveDate))` per new pair.
7. Return `StageResult(rowsIn = incoming section rows, rowsOut = rows appended, rowsRejected)`. Do not call `RunMetrics.record`.

Recalls: `RecallIncrementalStage` (`name = "incremental.recalls"`, `cadences = Set(Weekly)`, conf `after = []`).

8. `RecallRefresh.openNumbers(current: Dataset[RecallClean]): Seq[String]`: `recallNumber`s whose `status` is not closed. Closed = `Completed` or `Terminated`, compared case-insensitively. These are believed to be openFDA's values (`Ongoing`, `Completed`, `Terminated`, sometimes `Pending`); check the distinct values in `silver.recall`. Read the closed set from `Settings.config` key `medsignal.recalls.closedStatuses` and the batch size of step 9 from `medsignal.recalls.fetchBatchSize` (default 25), both with defaults in `conf.d/C3.conf`.
9. Fetch with I7's client:
   - records with `report_date` after `RunManifest.watermark("incremental.recalls")` (first run: the stage does nothing and tells the user to run `full` first);
   - the open recalls by number. Whether the API accepts a search on `recall_number` with several values joined by `OR`, and how long the query may be, is not verified: read the openFDA query documentation and I7's client. Use batches (start with 25 numbers). If I7 only offers the bulk file, download it and filter to these numbers plus the new report dates.
   Do not assume `report_date` changes when a recall's status changes; that is why the open ones are re-fetched.
10. `Delta.append` the fetched `RecallRaw` rows to bronze.
11. `RecallRefresh.dedupe(batch)`: one row per `recall_number`; if the two fetches returned the same recall, they are identical, keep either. Convert with S5's normalizing function (drug resolution through `drug_xref` included) into `Dataset[RecallClean]`; rows it cannot use become rejects as S5 defines.
12. `Delta.merge(clean, Tables.silver("recall"), Seq("recallNumber"))`.
13. `RunManifest.record("incremental.recalls", ctx.runId, checksum = "", watermark = Some(max reportDate in silver))`. Return `StageResult(rowsIn = fetched, rowsOut = merged, rowsRejected)`; do not call `RunMetrics.record`.
14. For tests, the fetch is a function parameter (`fetch: RecallQuery => Seq[RecallRaw]` or the shape I7 exposes), so no test calls the network.

Script: `scripts/run-labels.sh`.

15. A POSIX shell script (`set -eu`) run from the repository root before `run daily`. Usage: `scripts/run-labels.sh [data-dir]` (default `data`). It runs, in order, the I4 download command and the I5 extract command of the `labels` module, each with `--data-dir <data-dir>`, for example `sbt "labels/runMain <I4 main class> --data-dir $DATA_DIR"`; read the real main class names and arguments from the I4 and I5 code. It stops with a non-zero exit code if either command fails, so the daily run does not start on half-written files. `labels` keeps its own `data/raw/dailymed/manifest.tsv` and writes rejects to `data/interchange/labels/rejects.jsonl`; the script does not touch `RunManifest` and does not start the pipeline. Print one line per step and the number of JSON Lines files present at the end.

## Tests

`LabelIncrementalStageSpec` (`SparkTestSession`, fixtures in `C3/`):

- "a new label version triggers extraction for that version only": load day 1 (two labels), run this stage then L5's extraction function; load day 2 (one new version of the first label); run both again. L5's manifest gains exactly one unit, and `gold.LabeledReaction` rows of the other label are untouched.
- "the reference flag moves to the new version" (through S4's function).
- "a second run with the same files does nothing": zeros, bronze unchanged.
- "an unusable line becomes one reject".

`RecallRefreshSpec` (no network):

- "open numbers exclude completed and terminated recalls".
- "dedupe keeps one row per recall number".

`RecallIncrementalStageSpec`:

- "a status change on a recall is captured": week 1 has `R1` `Ongoing`; week 2's fetch returns `R1` `Terminated` with a termination date. After the run `silver.recall` has one `R1` row, status `Terminated`, `terminationDate` set.
- "a new recall after the watermark is inserted and the watermark advances".
- "an open recall is re-fetched even when its report date is old": the fake fetch records the numbers it was asked for.
- "without a watermark the stage does nothing and says to run full".
