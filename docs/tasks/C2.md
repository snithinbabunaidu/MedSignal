## Goal

A quarterly stage that loads one new FAERS quarter without reprocessing the old ones: parse it into its own bronze partition, merge its cases into `silver.case` when the version is newer, update the case detail tables for the affected cases, then rebuild the gold aggregates in full. A test proves the result equals a full rebuild, row for row. This is the project's main incremental-correctness claim (criterion 4) and half of the batch-speed claim (criterion 3).

## Implementation steps

1. Stage `FaersIncrementalStage` (`name = "incremental.faers"`, `cadences = Set(Quarterly)`). `stages/incremental.faers.conf`: `class = "medsignal.incremental.faers.FaersIncrementalStage"`, `after = ["bronze.rxnorm"]` (the stage names of other tasks are fixed in contracts.md, "Stage names").
2. `NewQuarters.pending(downloaded: Set[String], inBronze: Set[String], done: Set[String]): Seq[String]` (pure): quarters downloaded and not in `done`, sorted ascending (`2024Q3` sorts correctly as a string). `downloaded` comes from I1's manifest entries or public function; `inBronze` from the distinct `quarter` values of `bronze.faers_demo`; `done` from `RunManifest.loaded("incremental.faers")`. With `ctx.asOfQuarter = Some(q)`, keep only quarters `<= q`. If the list is empty, return `StageResult(0, 0, 0)`.
3. For each pending quarter, in order, one at a time:
   1. Bronze: if the quarter is not in `inBronze`, call I2's function that parses one quarter and appends its partitions (rejects are written by I2). If it is already there, skip parsing; never append a quarter twice.
   2. `CaseMerge.candidates`: from the quarter's `bronze.faers_demo` rows, one row per `caseid` using S1's rule and S1's function that turns `FaersDemo` into `Case`. `Case.quarter` is the quarter of `init_fda_dt`, then `fda_dt`, then the file quarter (contracts.md final section, item 11), so a follow-up version loaded from a later file keeps the case in its first quarter; S1's function does this, do not set `quarter` from the file being loaded.
   3. `CaseMerge.newer(candidates: Dataset[Case], current: Dataset[Case]): Dataset[Case]`: left-join on `caseid`; keep a candidate when there is no current row or `candidate.caseversion > current.caseversion`. For equal versions apply S1's tie rule exactly (read it; contracts.md does not define it). Then `Delta.merge(newer, Tables.silver("case"), Seq("caseid"))`.
   4. Deletions: `caseid`s in the quarter's `bronze.faers_deleted` are removed from `silver.case` with `DeltaTable.forPath(spark, path).as("t").merge(deleted.as("d"), "t.caseid = d.caseid").whenMatched().delete().execute()` (verify the API). A deleted case must also not be re-inserted by step 3.3, in this or any later quarter: a `caseid` on any deleted list is removed (item 12), so remove the ids of the whole `bronze.faers_deleted` table from the candidates first, as S1 does.
   5. Affected cases = merged ids plus deleted ids. `CaseDetailRefresh`: for each of `case_drug`, `case_reaction`, `case_outcome`, `case_indication`, delete the rows of affected `caseid`s (same Delta delete-by-join), then append the rows S3's functions build for the merged cases from the winning `primaryid`'s bronze rows. Call S2's resolver first so new drug name strings are in `drug_xref`; it resolves only new strings.
   6. `RunManifest.record(...)` for the quarter, after all writes succeeded.
4. After the last quarter: call G1's and G3's build functions to rebuild `gold.AdverseEventStat` and `gold.Signal` from silver. G3 writes default labeled-status and triage columns (item 16); L5's stage `labeltext.status` and A4's stage `triage.status` run after this stage and merge their columns back in the same run.
5. Metrics: return `StageResult(rowsIn = DEMO rows read, rowsOut = cases merged, rowsRejected = rejects for these quarters)`. Do not call `RunMetrics.record`; the runner records (item 6).
6. Failure handling: a crash between steps leaves the quarter out of the manifest; the next run repeats it. Every step must therefore be safe to repeat: bronze is skipped when present, the merge and the delete-then-append are idempotent.

## Tests

Fixtures: three quarters of about 10 cases each, built to contain: a case re-sent in a later quarter with a higher `caseversion` and a different drug list; a case whose later copy has a lower `caseversion`; a case on a deleted list after it was loaded; a drug name string first seen in the last quarter; one malformed line.

`CaseMergeSpec` (`SparkTestSession`):

- "a newer version replaces the case": version 2 after version 1 leaves one row with `caseversion = 2`.
- "an older version arriving later is ignored".
- "a deleted case disappears from case and from every detail table".
- "a new case is inserted".

`IncrementalEqualsFullSpec`:

- "gold after loading quarters one by one equals gold after a full rebuild, row for row": path A loads the three quarters into one temp dataDir with the full-rebuild functions of I2, S1, S2, S3, G1, G3; path B runs `FaersIncrementalStage` three times in a second dataDir, one quarter each. For `silver.case`, the four detail tables, `gold.AdverseEventStat` and `gold.Signal`: counts are equal and `a.except(b)` and `b.except(a)` are both empty. If `Signal` differs only in the last digits of a `Double`, compare those columns with a tolerance of 1e-9 and say so in the results file; do not loosen any other column.
- "loading two quarters in one run equals loading them in two runs".

`FaersIncrementalStageSpec`:

- "a second run with no new quarter does nothing": zeros, and the Delta version of `silver.case` is unchanged.
- "a repeated quarter after a simulated crash does not duplicate rows": remove the manifest entry and run again; tables are unchanged.
- "as-of limits the quarters loaded".
