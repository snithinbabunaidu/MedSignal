## Goal

One page that a reader who has never seen the repository can read in five minutes and then explain how MedSignal works and why it is built this way. It is a required hand-in of the brief (see `docs/acceptance-criteria.md`, "Hand-ins from the brief").

## Context

- Read `docs/architecture.md` (the source for almost everything here), `docs/ontology.md`, `docs/project-plan.md` section "Scope", `docs/contracts.md` final section, and `docs/decisions/` if it exists.
- The note describes what was built, not what was planned. Before writing, compare `docs/architecture.md` with the code: the stage files in `pipeline/src/main/resources/stages/`, the gold case classes, the spike decisions F4 and F5. Where they differ, the code wins, and the difference is listed in `docs/results/D1.md` (do not edit `architecture.md` from this branch).
- "One page" means one printed A4 or Letter page, diagrams included. That is the hard limit; the word limit below serves it.
- One engineer drafts sections 1 and 2, the other sections 3 and 4; each reviews the other's half.

## Inputs

- The documents above and the merged code.
- Measured numbers from `docs/results/*.md` (use at most three; each must cite its file).

## Outputs

`docs/architecture-note.md`, at most 450 words of prose outside diagrams and tables, with exactly this outline:

```
# MedSignal: architecture note
One sentence: what the system does and for whom.

## 1. Data flow
One Mermaid flowchart (left to right): sources -> parse -> bronze -> silver -> gold -> serving DB -> API -> pages,
with the triage write-back as a dotted arrow. At most 14 nodes.
Two or three sentences: what each layer guarantees.

## 2. Ontology
One Mermaid erDiagram: Drug, Label, LabeledReaction, AdverseEventStat, Signal, Recall, ChangeEvent, TriageDecision.
Entity names and links only, no field lists. One sentence: everything links by rxcui.

## 3. The four decisions that mattered
A numbered list, one to two sentences each: the decision, then what it bought.
  1. Identity once, in silver.
  2. Incremental where it is expensive, full where it is cheap.
  3. The text step is keyed by label version and extractor version.
  4. Serving is separate from Spark.

## 4. What we chose not to do
A short list with one reason each.
```

## Files to create

- `docs/architecture-note.md`.
- `docs/results/D1.md`: word count, how the one-page check was done, differences found between `architecture.md` and the code.

## Implementation steps

1. Start both diagrams from the ones in `docs/architecture.md` and `docs/ontology.md`, then cut. Drop version numbers from node labels. Leave phase 6 objects (`SignalHistory`, `BacktestResult` and the rest) out of the diagram; mention them in one clause.
2. Section 3: take the four decisions from `docs/architecture.md` "Decisions that matter most". Give each one concrete consequence taken from the project, for example: an override added to the identity file fixes every downstream table on the next run; a new FAERS quarter never re-reads a label; the app stays readable during a publish. Where a number exists (criterion 4, quarter run time), quote it with its results file.
3. Section 4: take the list from `docs/project-plan.md` "Out of scope" and the decisions made on the way. It must include: no Palantir Foundry (Delta Lake and plain Spark instead); no LLM or other AI step (a rule-based label reader with stored passages instead, so every result can be checked); no streaming (the fastest source is daily); no user accounts; case-level rows kept out of gold. One reason each, in a few words.
4. Write in plain present tense. No history of how the design evolved, no library tutorial, no list of every table.
5. Check the page: render the Markdown (GitHub preview or the IDE), print to PDF at default margins, confirm one page and that both diagrams are readable at that size. Check that both Mermaid blocks render on GitHub.
6. Count words outside code fences and tables; record the count.
