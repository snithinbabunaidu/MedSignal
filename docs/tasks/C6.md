## Goal

A measurement task. Measure one pipeline, FAERS raw text to `gold.AdverseEventStat`, before and after three changes, one change at a time on the same machine, and write the numbers and what did not help to `docs/optimization-log.md`. The log is a hand-in of the course brief and is criterion 14; its timings also support criterion 3.

## Context

Read `docs/acceptance-criteria.md` criteria 3 and 14, `docs/pipeline-spec.md` sections 1, 3, 4 and 6, `docs/setup.md`, and briefs `docs/tasks/I2.md`, `S1.md`, `S3.md`, `G1.md`, `C1.md`, `C2.md`.

Facts and decisions this brief fixes:

- No production code is written or changed. The optimized forms already exist in the pipeline (Delta bronze partitioned by quarter, broadcast formulary, incremental load). The "before" of each change is produced by switching the optimization off for a measurement run, with a Spark setting where one exists or with a short `spark-shell` script that calls the tasks' public functions. Scripts are not committed; the exact commands and settings go into the log.
- The measured path: raw FAERS files, parse (I2), `silver.case` (S1), `drug_xref` and case detail (S2, S3), `gold.AdverseEventStat` (G1). Signals, labels and recalls are outside it.
- Numbers come from the Spark UI of the run (history server or the live UI on port 4040; see `docs/setup.md`): wall time from the Jobs page, shuffle read and write bytes summed over stages from the Stages page, peak executor memory from the Executors page. Where exactly peak memory is shown differs between Spark versions; check the Spark 4.0 monitoring documentation and name the column used. If it is not available in local mode, say so and record the peak JVM heap another way, stating how.
- One change at a time: each row's "before" is the previous row's "after". Same machine, same data, same Spark settings otherwise, nothing else running. Run each variant three times and report the median; discard a first run that includes a cold file cache.
- State the data size (quarters, raw bytes, DEMO rows) and the machine (CPU, cores, RAM, disk, OS, JDK, Spark version, driver memory, `local[N]`).

## Implementation steps

1. Baseline. Raw text read and parsed in the same job that builds silver and gold: no Delta bronze, all columns carried, broadcast joins off (`spark.sql.autoBroadcastJoinThreshold=-1` and no `broadcast` hint), every quarter processed. Record the three numbers.
2. Change 1, columnar bronze with column pruning. Bronze written once as Delta partitioned by `quarter`; silver reads only the columns it needs. Measure the silver and gold build from bronze, and report the one-off bronze write separately. Confirm pruning in the physical plan (`ReadSchema` in `explain`) and quote that line.
3. Change 2, broadcast joins for the formulary and `drug_xref`. Restore the default threshold and the hints. Confirm `BroadcastHashJoin` replaced `SortMergeJoin` in the plan for both joins; note the size of each broadcast table. If `drug_xref` is too large to broadcast, say so and report only the formulary.
4. Change 3, incremental quarter load against full rebuild. With all but the newest quarter loaded, measure `run quarterly` for the one new quarter (C2) against `run full`.
5. What did not help. Measure at least these two and report them even when the difference is nil or negative:
   - shuffle partition count: `spark.sql.shuffle.partitions` at 200 and at two other values, with adaptive query execution on (expected: little effect, because adaptive execution coalesces partitions; verify);
   - caching: `persist` on the case detail dataset reused by the G1 aggregations, against no caching.
6. Write the log with exactly this layout:

   ```markdown
   # Optimization log

   ## Setup
   Machine, software versions, Spark settings, data size, how each number was read.

   ## Results

   | Step | Change | Wall time (s) | Shuffle read (MB) | Shuffle write (MB) | Peak executor memory (MB) | Change in wall time | Kept |
   |---|---|---|---|---|---|---|---|
   | 0 | Baseline: raw text, no pruning, no broadcast, full | | | | | n/a | n/a |
   | 1 | Delta bronze by quarter, column pruning | | | | | | yes/no |
   | 2 | Broadcast formulary and drug_xref | | | | | | |
   | 3 | Incremental quarter load (one quarter) | | | | | | |

   ## What did not help

   | Candidate | Setting tried | Wall time (s) | Shuffle (MB) | Peak memory (MB) | Compared with | Why it did not help |
   |---|---|---|---|---|---|---|

   ## Notes per step
   One short paragraph per step: what was changed, the command and settings, the plan line that proves it, the three run times behind the median.
   ```

   "Change in wall time" is a percentage against the row above (step 3 against step 2's full rebuild).

## Tests

No ScalaTest spec: this task adds no code. Checks done by hand and stated in the log:

- Each variant produces the same `gold.AdverseEventStat` as the normal pipeline (row count, and `except` in both directions is empty). A faster run with different output is not an optimization.
- Each claimed plan change is shown by a quoted `explain` line.
