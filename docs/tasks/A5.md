## Goal

A repeatable measurement of how long page requests take against a serving database published from the full formulary, and a results file with the 95th percentile. The target is 95% of requests under 1 second (acceptance criterion 8). The number is reported whether or not it meets the target.

## Context

- Read `docs/acceptance-criteria.md` row 8, `docs/contracts.md` section "HTTP API", and `docs/tasks/A3.md` section "Inputs" (which requests each page makes).
- A "page request" is every HTTP request a page makes when it loads: the HTML file plus its API calls. Measure each request, and also report per page the slowest request (the calls run in parallel in the browser, so that approximates when the page is complete).
- The measurement runs against a real, running app with the real published data. It must not run in CI, where no such database exists. It is a ScalaTest spec that cancels itself unless a base URL is supplied.
- Use the JDK HTTP client (`java.net.http.HttpClient`); it needs no new dependency.
- Measure on the laptop that will run the demo, with the app and the database both local. Record the machine (CPU, memory), the database (H2 or PostgreSQL) and the table sizes, because the number means nothing without them.

## Inputs

- A running app (A2) on a database published by A1 from the full data.
- Environment variable `MEDSIGNAL_PERF_URL` (for example `http://localhost:8080`). Optional: `MEDSIGNAL_PERF_REQUESTS` (default 200 per request type), `MEDSIGNAL_PERF_CONCURRENCY` (default 8).
- The request mix, discovered at run time so it covers the whole formulary:

  | Page | Requests |
  |---|---|
  | Today | `/index.html`, `/api/changes`, `/api/health`, `/api/recalls?status=open` |
  | Signals | `/signals.html`, `/api/signals?labeled=unlabeled&status=open`, `/api/signals?limit=1000`, `/api/signals?class=<each class>` |
  | Drug drill-down | `/drug.html`, `/api/drugs/<rxcui>` for every distinct `rxcui` returned by `/api/signals?limit=1000` |
  | Recalls | `/recalls.html`, `/api/recalls?status=open` |
  | Pipeline health | `/health.html`, `/api/health` |

  `POST /api/triage` is not measured: it would write real decisions into the serving database.

## Outputs

- Console table and `docs/results/A5.md`: per request type and overall, the count, errors, p50, p95, p99 and maximum in milliseconds, for the sequential pass and the concurrent pass.
- The share of all requests under 1000 ms: this is the number for criterion 8.

## Implementation steps

1. Percentiles (nearest-rank, so the result is always an observed value):

   ```scala
   object Percentiles:
     /** p in (0, 100]; returns None for an empty sample. */
     def percentile(sortedMs: Vector[Long], p: Double): Option[Long] =
       if sortedMs.isEmpty then None
       else Some(sortedMs(math.max(0, math.ceil(p / 100.0 * sortedMs.size).toInt - 1)))
     def shareUnder(ms: Vector[Long], limitMs: Long): Double
   ```

2. `LoadRunner`:

   ```scala
   final case class Timing(label: String, path: String, status: Int, millis: Long)
   object LoadRunner:
     def get(client: HttpClient, base: String, label: String, path: String): Timing
     def run(base: String, requests: Vector[(String, String)], concurrency: Int): Vector[Timing]
   ```

   Time with `System.nanoTime` around `client.send(...)` reading the full body (`BodyHandlers.ofByteArray`), so the time includes transfer. For concurrency use a fixed thread pool and `Future`s; no `var`.

3. `ApiLatencySpec` flow:
   1. `assume(sys.env.contains("MEDSIGNAL_PERF_URL"))` so the spec is cancelled, not failed, in CI.
   2. Discover the classes and rxcuis from `/api/signals?limit=1000` (parse with circe, already on the classpath).
   3. Warm-up: send each request type 20 times and discard the timings (JIT, connection pool, database cache).
   4. Sequential pass: each request type `MEDSIGNAL_PERF_REQUESTS` times; drill-down requests cycle through every rxcui so the whole formulary is hit at least once.
   5. Concurrent pass: the same list shuffled with a fixed seed, at the configured concurrency.
   6. Print the table. Count any non-200 response as an error and list it; errors are not dropped from the report.
   7. Assert only that there were no errors and that at least one request ran. Do not assert the 1-second target in the spec: the criterion is "measured and reported", and a hard failure would hide the number.

4. Run it:

   ```bash
   # terminal 1, after a full pipeline run and publish
   sbt app/run
   # terminal 2
   MEDSIGNAL_PERF_URL=http://localhost:8080 sbt "app/testOnly medsignal.perf.ApiLatencySpec"
   ```

5. If the p95 is above 1 second, look for the cause before reporting: the slowest request type, missing index (compare with the indexes in `docs/tasks/A1.md`), response size of `/api/drugs/{rxcui}`. Fixes belong to A1 or A2 as their own pull requests; record in the results file what was found and the number before and after.

6. Write `docs/results/A5.md` with: date, commit hash, machine, database kind and version, row counts of `signal`, `adverse_event_stat`, `labeled_reaction`, the two tables of timings, the share under 1 second, and one sentence stating whether criterion 8 is met.

## Tests

- `PercentilesSpec` "p95 of 1..100 is 95"; "p50 of (10, 20, 30) is 20"; "p100 is the maximum"; "empty sample gives None"; "shareUnder(Vector(500, 900, 1500, 2000), 1000) is 0.5".
- `ApiLatencySpec` "is cancelled when MEDSIGNAL_PERF_URL is absent" (seen as "canceled" in the CI output); "reports percentiles for every request type" (run by hand).

No fixture files are needed.

## Out of scope

- Changing the API or adding indexes (A2, A1).
- Browser rendering time; only HTTP request time is measured.
- Pipeline batch speed (criterion 3, tasks C2 and C3).
- Load beyond a single user's realistic use; this is not a stress test.
