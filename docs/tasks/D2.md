## Goal

One document that states, for each of the 14 acceptance criteria, the number that was measured, whether the target was met, how it was measured, and where the evidence is. The project plan promises that every criterion is measured and reported "whether or not we reach it"; this report is where that promise is kept.

## Context

- Read `docs/acceptance-criteria.md` (the 14 rows and targets) and `docs/branching.md` row "`docs/data-issues.md`, `docs/acceptance-criteria.md`": feature branches do not edit the criteria file; each task wrote its numbers to `docs/results/<task id>.md`, and this task collects them.
- This task collects; it does not measure. If a number is missing or stale, the owner of that task re-runs the measurement and updates their results file in their own pull request first.
- No blank cells. A missed target is written as "not met" with the number. A criterion whose task never ran is written as "not measured" with the reason, and that blocks the done condition.
- Split: Nithin fills criteria 1 to 4, 10, 11, 13, 14; Zenish fills 5 to 9 and 12. Each checks the other's rows against the source files.

## Outputs

`docs/acceptance-report.md` with this layout:

```
# Acceptance report
Measured on <date>, commit <short hash>, machine <CPU, cores, memory>, data <first quarter> to <last quarter>.

## Summary
<n> of 14 met, <n> not met. One line per criterion not met: the number and the main reason.

## Results
| # | Criterion | Target | Measured | Result | How measured | Source |
|---|---|---|---|---|---|---|
| 1 | Data accounted | 100% of lines loaded or rejected | 100% (1,234,567 of 1,234,567 lines; 812 rejected) | met | Sum of lines in = loaded + rejected per file, stage bronze.faers | [I2](results/I2.md) |

## Notes per criterion
One short paragraph each, only where the number needs a caveat.

## Hand-ins
| Hand-in | Where | Present |
```

Column rules: `Target` copied word for word from `acceptance-criteria.md`; `Measured` always holds a number with its unit and, for a share, the numerator and denominator; `Result` is exactly `met`, `not met` or `not measured`; `How measured` names the test, command or query in one sentence; `Source` links the results file. The example row above shows the form only; its numbers are invented and must not be copied.

## Implementation steps

1. Check that every source file in the mapping exists and contains the number. List gaps to the owning engineer before writing.
2. Criteria with several parts get every part in `Measured`, and are `met` only if all parts are: 3 (full rebuild, one quarter, daily run: three times), 5 (precision, recall, negation accuracy), 9 (spec per stage, CI green, coverage), 10 (share and median lead).
3. Criterion 3: state the machine. If it was not an 8-core laptop, say so in the notes.
4. Criterion 9: for "every statistic and pipeline stage has a spec", list the stage names from `pipeline/src/main/resources/stages/` and tick each against a spec file; give the count. Take coverage from the scoverage report of the latest CI run on `main`, not a local run.
5. Criterion 10: copy V2's headline and, in the notes, its `medianLeadEverFlagged` and the small-sample caveat. Criterion 13: give both PR-AUC values and the ratio.
6. All numbers must come from the same data range. If a results file was measured on different data (for example the Docker sample), mark it and ask for a re-run.
7. Hand-ins table: working build (`docker compose up`), architecture note, optimization log, demo script; each with its path and whether it is present.
8. Never round a miss into a pass: 89.6% against a 90% target is `not met`.

- Changing a target after seeing the number.
